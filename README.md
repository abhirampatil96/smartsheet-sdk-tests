# Smartsheet SDK Contract Testing with WireMock

This repository provides a standalone [WireMock](http://wiremock.org/) server implementation for contract testing the Smartsheet SDKs. The server is preloaded with a set of JSON mappings (in the [`mappings/`](mappings/) directory) that simulate the Smartsheet API. This setup allows us to run tests for all Smartsheet SDKs and ensure consistent behavior and validate API contracts without relying on the live API.

## How does it work?

- The WireMock server is loaded with JSON mappings from the [`mappings/`](mappings/) directory.
- Each mapping defines a request to match and a response to return.
- We use a convention of including these two headers in requests:
  - `x-test-name` - used for exact mapping matches, allowing us to target different mock responses even if they share the same HTTP method and endpoint.
  - `x-request-id` is a UUID generated for each request, which helps us trace requests in the WireMock admin history (since we don't have access to the UUIDs generated by WireMock itself).
- Catch-all path patterns are used for test cases that are common to all API endpoints (e.g., `/errors/500-response`).

## Running WireMock

To start the WireMock server with the provided mappings:

```sh
docker compose up
```

This will start a container with a WireMock server on [http://localhost:8082](http://localhost:8082) with the mappings mounted from the [`mappings/`](mappings/) directory.

## Common Test Cases

| HTTP Method | Test Case | Notes | Response Code |
|---|---|---|---|
| GET | Verify if the path generated in the SDK is correct | Test case can use any mapping, the goal is to check if the path generated by the SDK method is correct. | 2XX |
|  | Verify if the query params generated in the SDK are correct | Test case can use any mapping, the goal is to check if the query parameters in the url generated by the SDK method are correct. | |
|  | Test if the response body deserializes properly with all properties | The goal is to simulate a response that includes all response body properties and check whether they are deserialized properly | |
|  | Test if the response body deserializes properly with required only properties | The goal is to simulate a response that includes all required response body properties only and check whether they are deserialized correctly | |
| POST | Verify if the path generated in the SDK is correct | Test case can use any mapping, the goal is to check if the path generated by the SDK method is correct. | |
|  | Test if the response body deserializes properly with all properties | The goal is to simulate a response that includes all response body properties and check whether they are deserialized properly | |
|  | Test if the request body sent is correct | The goal is to get the body from the request that is sent and verify that it is correct | |
| DELETE | Verify if the path generated in the SDK is correct | Test case can use any mapping, the goal is to check if the path generated by the SDK method is correct. | |
|  | Test if the response body deserializes properly with all properties | The goal is to simulate a response that includes all response body properties and check whether they are deserialized properly | |
| ANY | Test if the response body deserializes properly with a 400 error response | Uses the general `/errors/400-response` mapping, the goal is to simulate a 400 error response and check if it is deserialized properly | 4XX |
|  | Test if the response body deserializes properly with a 500 error response | Uses the general `/errors/500-response` mapping, the goal is to simulate a 500 error response and check if it is deserialized properly | 5XX |
